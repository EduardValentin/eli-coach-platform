## Shape

The business rules live in `packages/domain` (C1), published as nine subpaths with no root barrel: one folder per entity (`account`, `acquisition`, `cart`, `download-grant`, `email-address`, `feature-flag`, `product`, `waitlist`) plus the interface-only `shared`. Rules are methods on the entity classes that carry the decisions — account lifecycle and portal access (`Account#isActive`), waitlist availability and reduced-pricing allocation, delivery limits and their windows, download-grant validity and delivery shape, publication slug, taxonomy, size-cap, digest and target rules, cart reconciliation, purchasability (`Product.evaluatePurchasability`), file-format resolution, and email normalization (`EmailAddress`) — and `<Verb><Noun>UseCase` classes, each with one `execute` method, sequence them. Eight gateway ports (`Accounts`, `WaitlistEntries`, `StoreCatalog`, `StoreAcquisitions`, `DownloadGrants`, `StoreProductPublications`, `FeatureFlags`, `ProductAssets`) plus the writer, digest and token ports and the five cross-cutting `shared` ports (`Clock`, `Logger`, `BotVerifier`, `ProductEmail`, `ManagementAuthenticator`) are all named in domain language and owned by policy. The package declares no dependencies and its tsconfig sets `"types": []`, so neither an import nor an ambient Node global reaches inside it.

Details plug in through those ports. Each feature under `apps/platform/src/features/<feature>/` holds its Postgres repositories (`data/`), email adapters (`email/`), HTTP controllers and route modules (`api/`), route fragment (`routes.ts`), wire schemas and path literals (`contracts/`), request-context key and guards (`server/guards/`), its composition (`server/<feature>-composition.server.ts`) and its browser code (`ui/<slice>/`, with presenters and step machines in `ui/shared/` and `ui/public/`). `packages/infrastructure` (C6) holds adapters and factories only — Turnstile bot detection, Resend and in-memory product email, bearer-secret management auth, the feature-flag repository, HTTP helpers, PWA definitions — and owns no port. `packages/test-support` (C16) is a dev-only fixture package no production package declares. `packages/db`, `packages/config`, `packages/content` and `packages/ui` are leaf packages; `packages/ui` publishes six concern subpaths and the stylesheet with no root barrel. The single composition root is `apps/platform/src/server/container.server.ts`, memoised behind `getPlatformContainer()` and imported only by `root.server.ts`: it builds the shared handles once and calls the four feature compositions. Routes and loaders read their feature's request-context key (`accountsContext`, `sessionContext`, `storeContext`, `waitlistContext`, `platformContext`, `runtimeConfigContext`) off `args.context` instead of resolving anything from a container. Surfaces (`public-site`, `client-portal`, `coach-portal`) assemble features into products and own only route modules, shells and sections.

Boundaries are enforced by three tools. `tools/dependency-cruiser.config.cjs` declares 36 forbidden rules — package export maps and dependency-absence for the workspace packages, and named rules for every app-level boundary (feature internals, surface-to-feature and surface-to-surface, composition root, browser half, route thinness, guards, domain slices, infrastructure subpaths, UI layering, workspace-by-name, stability and five hygiene rules) — `knip.json` holds published surfaces at zero unused exports, files, dependencies and unlisted dependencies, and `tools/domain-layout.mjs` checks the domain package's per-entity folder layout. All three run in `pnpm check:boundaries`, which runs inside `pnpm typecheck`, `pnpm build`, every vitest run (through `vitest.global-setup.mts`) and the Docker builder stage, so a crossing fails the build and the image. `tools/boundaries.test.mjs` proves the dependency-cruiser rules against `tools/boundary-fixtures/`: 35 of the 36 rules have a fixture, and `stability` has none because `moreUnstable` needs dependent counts a fixture tree cannot express — the real-tree cruise is its only proof. `tools/domain-layout.test.mjs` proves the domain-layout rules against `tools/domain-layout-fixtures/`. Two rules stay review-owned by decision: controller shape (no base controller, no per-request instance field) and failure mapping (an adapter never swallows an infrastructure failure into a result-union member; exactly one named expected condition — ENOENT in the filesystem asset store — may be classified). The component graph has no cycles at module, component, domain-slice or UI-subpath level.

## Reading this folder

- `components.md`: the enforced units and what each publishes.
- `units.md`: classes, modules, functions, interfaces, and data structures, with their kind and ring.
- `dependencies.md`: every source dependency, the forbidden edges, the ports, entry points, and shared data shapes.
- `metrics.md`: stability and abstractness per component; volatility counts the 48 commits in `148d594f..871196af`.
- `decisions.md`: deferred decisions, accepted trade-offs, intended exceptions, accepted findings.
- `conventions.md`: where a file goes and what it may import; the folder layout the dependency rules assume.

Terms: a *unit* is a class, module, function, interface, or data structure. A *component* is a group of units behind one published interface that tooling enforces. An *edge* from A to B means A's source code names B. *Policy* is business rules; *detail* is databases, frameworks, transports, vendors, UI, and the data shapes they produce. A *ring* is a band of units at one level of distance from inputs and outputs; dependencies point inward.
