## Shape

The business rules live in `packages/domain` (C1), published as nine subpaths with no root barrel: one folder per entity (`account`, `acquisition`, `cart`, `download-grant`, `email-address`, `feature-flag`, `product`, `waitlist`) plus the interface-only `shared`. Rules are methods on the entity classes that carry the decisions — account lifecycle and portal access (`Account#isActive`), waitlist availability and reduced-pricing allocation, delivery limits and their windows, download-grant validity and delivery shape, publication slug, taxonomy, size-cap, digest and target rules, cart reconciliation, purchasability (`Product.evaluatePurchasability`), file-format resolution, and email normalization (`EmailAddress`) — and `<Verb><Noun>UseCase` classes, each with one `execute` method, sequence them. Eighteen published ports and one unpublished one are named for their consumers' capabilities: eight gateways (`Accounts`, `WaitlistEntries`, `StoreCatalog`, `StoreAcquisitions`, `StoreProductPublications`, `DownloadGrants`, `FeatureFlags`, `ProductAssets`), the two email ports (`WaitlistConfirmation`, `ProductDelivery`), the writer, digest and hasher ports (`ProductAssetWriter`, `ProductAssetDigest`, `PayloadDigestGenerator`, `DownloadTokenHasher`), the input boundary `FeatureFlagReader`, `Clock` as the sole `shared` port, and `AcquisitionIncidents` and `WaitlistIncidents` beside the use cases that consume them. `DownloadTokenGenerator` remains deliberately unpublished because its only consumer is inside the package. Waitlist mode is persisted policy input, not deployment configuration: `Waitlist` is the configured waiting-list aggregate whose cap and active offer are shared by availability and registration, and `GetWaitlistUseCase` reads the existing `FeatureFlagReader` on every execution, reads `WAITLIST_MODE` from the published `FeatureFlagSet` (true enables, false or absent disables), and assembles the plain `WaitlistSnapshot` from that mode, the entity's offer and its computed availability. A failed flag read is reported through `WaitlistIncidents.waitlistModeReadFailed()` and safe-enables the waitlist with availability unknown. The resulting `waitlist → feature-flag` edge enters the sibling's index, stays in the use-case ring and closes no cycle. The offer object is readonly but not deeply immutable; that R17 cost is accepted until offer mutation or a second offer model is required. The package declares no dependencies and its tsconfig sets `"types": []`, so neither an import nor an ambient Node global reaches inside it.

Details plug in through those ports. Each feature under `apps/platform/src/features/<feature>/` holds its Postgres repositories (`data/`), email adapters (`email/`), HTTP controllers and route modules (`api/`), route fragment (`routes.ts`), wire schemas and path literals (`contracts/`), request-context key and guards (`server/guards/`), its composition (`server/<feature>-composition.server.ts`) and its browser code (`ui/<slice>/`, with presenters and step machines in `ui/shared/` and `ui/public/`). `packages/infrastructure` (C6) holds adapters and factories — Turnstile bot detection, Resend and in-memory product email, bearer-secret management auth, the feature-flag repository, HTTP helpers and PWA definitions — and owns the three adapter-facing contracts `BotVerifier`, `ProductEmail` and `ManagementAuthenticator` inside their matching concerns. `packages/test-support` (C16) is a dev-only fixture package no production package declares. `packages/db`, `packages/config`, `packages/content` and `packages/ui` are leaf packages; `packages/ui` publishes six concern subpaths and the stylesheet with no root barrel. The application composition root is `apps/platform/src/server/container.server.ts`, memoised behind `getPlatformContainer()` and imported only by `root.server.ts`: it builds the shared handles once, including one `createConsoleLogger()` that implements both domain incident interfaces and one `PostgresFeatureFlagRepository` behind one stateless `GetFeatureFlagsUseCase`, and calls the three feature compositions (`accounts`, `store`, `waitlist`), handing the same feature-flag reader to `composePlatformFeature` and `composeWaitlistFeature`; `platform-composition.server.ts` constructs no persistence. The platform feature-flag API and the public-site shell each execute that reader per request, with no result cache and no production write path. Routes and loaders read their feature's request-context key (`accountsContext`, `sessionContext`, `storeContext`, `waitlistContext`, `platformContext`, `runtimeConfigContext`) off `args.context` instead of resolving anything from a container. Surfaces (`public-site`, `client-portal`, `coach-portal`) assemble features into products and own only route modules, shells and sections.

Boundaries are enforced by three tools. `tools/dependency-cruiser.config.cjs` declares 35 forbidden rules — package export maps and dependency-absence for the workspace packages, and named rules for every app-level boundary (feature internals, surface-to-feature and surface-to-surface, composition root, browser half, route thinness, guards, domain slices, infrastructure subpaths, UI layering, workspace-by-name, stability and five hygiene rules) — `knip.json` holds published surfaces at zero unused exports, files, dependencies and unlisted dependencies, and `tools/domain-layout.mjs` checks the domain package's per-entity folder layout. All three run in `pnpm check:boundaries`, which runs inside `pnpm typecheck`, `pnpm build`, every vitest run (through `vitest.global-setup.mts`) and the Docker builder stage, so a crossing fails the build and the image. `tools/boundaries.test.mjs` proves the dependency-cruiser rules against `tools/boundary-fixtures/`: 34 of the 35 rules have a fixture, and `stability` has none because `moreUnstable` needs dependent counts a fixture tree cannot express — the real-tree cruise is its only proof. `tools/domain-layout.test.mjs` exercises `tools/domain-layout.mjs` against `tools/domain-layout-fixtures/` and against the real domain package; all six of the tool's checks have a failing fixture. Two rules stay review-owned by decision: controller shape (no base controller, no per-request instance field) and failure mapping (an adapter never swallows an infrastructure failure into a result-union member; exactly one named expected condition — ENOENT in the filesystem asset store — may be classified). The component graph has no cycles at module, component, domain-slice or UI-subpath level. Deployment adds artifact controls outside the dependency rules: the platform package's `files` allowlist emits only `build`, the config, content, domain, infrastructure and UI packlists keep production source and artifacts while excluding colocated test/spec files, and the Docker builder asserts that the deployed artifact contains `build/server/index.js`, has no top-level `src` or `e2e`, has no test/spec file under `node_modules/@eli-coach-platform`, and omits the dev-only test-support package. Environment, Docker, CI, integration and Lighthouse wiring no longer carry `WAITLIST_MODE`; migration 0018 seeds the persisted flag true, and E2E setup and teardown switch it through a test-only Postgres adapter that production imports cannot reach.

## Reading this folder

- `components.md`: the enforced units and what each publishes.
- `units.md`: classes, modules, functions, interfaces, and data structures, with their kind and ring.
- `dependencies.md`: every source dependency, the forbidden edges, the ports, entry points, and shared data shapes.
- `metrics.md`: stability and abstractness per component; volatility counts the 84 commits in `148d594f..e8690f45`, with the 16 of the domain-model restructure shown separately, plus PR #229; the `8ac6a613` change review recomputes C1, C6, C7, C8 and C14 and carries the other rows from run 8, and the waitlist-mode column counts the seven component-changing commits of `79fa1e95..f0eb1bf4` plus the main merge.
- `decisions.md`: deferred decisions, accepted trade-offs, intended exceptions, accepted findings.
- `conventions.md`: where a file goes and what it may import; the folder layout the dependency rules assume.

Terms: a *unit* is a class, module, function, interface, or data structure. A *component* is a group of units behind one published interface that tooling enforces. An *edge* from A to B means A's source code names B. *Policy* is business rules; *detail* is databases, frameworks, transports, vendors, UI, and the data shapes they produce. A *ring* is a band of units at one level of distance from inputs and outputs; dependencies point inward.
