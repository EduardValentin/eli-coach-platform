## Shape

The business rules live in `packages/domain` (C1): one folder per feature holding entities (`Account` and its portal-access predicates, waitlist availability bucketing, coaching-bundle display, store file-format and content-addressing rules), use-case services (`AccountProvisioningService`, `WaitlistService`, `StoreCatalogService`, `StoreAcquisitionService`, `DownloadGrantService`, `StoreProductPublicationService`, `FeatureFlagService`), the request, response, and model types they exchange, and seventeen gateway ports. The package declares no dependencies, so nothing outside the language can be imported there. Several services still carry clerk-level arithmetic (rate-limit windows, grant expiry, sub-address normalisation, publication size and slug rules) beside their sequencing, and some browser-side rules (cart reconciliation, catalog filtering, submission step machines) have no home in C1 yet.

Details plug in through those ports. Feature folders under `apps/platform/src/features/<feature>/` hold the Postgres repositories (`data/`), email adapters (`email/`), HTTP controllers and route modules (`api/`), server guards and middleware factories (`server/`), and browser code (`ui/`); `packages/infrastructure` (C6) holds cross-feature adapters (Turnstile bot detection, Resend email, bearer-secret management auth, feature flags, PWA definitions) and also declares the three ports those adapters implement, so those ports sit on the detail side rather than in C1. `packages/db`, `packages/config`, `packages/content`, and `packages/ui` are leaf packages nothing in scope depends on downward. The single composition root is `apps/platform/src/server/container.server.ts`, memoised behind `getPlatformContainer()`; `root.server.ts` composes Clerk and account-resolution middleware from it. Route modules and `.server.ts` loaders resolve their controllers from the container rather than being handed them, and two feature-level factories (`create-store-delivery-service`, `create-waitlist-confirmation-service`) plus `createProductEmailSender` and `createBotVerifier` construct details outside the root. Surfaces (`public-site`, `client-portal`, `coach-portal`) assemble features into products and own only route modules, shells, and sections.

Boundaries are enforced in three modes. Workspace packages are enforced by their `package.json` export maps (deep imports do not resolve; `infrastructure` publishes six subpaths and no root barrel) and, for C1, by the absence of any dependency. App-level components (features, surfaces, `server/`) are enforced only by ESLint `no-restricted-imports` regions R1 to R7, proven by `tools/lint-boundaries.test.mjs`: a crossing fails `pnpm lint`, not the build. Drawn but unenforced: every port's line between consumer and implementer (structural typing only; nothing stops a controller importing a repository class), the route-module thinness and centralised-authorization rules on ARCHITECTURE.md's human-review list, the `config/test-support` test-only subpath, the folders inside `packages/infrastructure`, and the `app` Postgres namespace that four components attach tables to. The component graph has one cycle family: `server` (C14) constructs every feature's controllers while feature route modules import the container getter and `http.server` helpers back from C14.

## Reading this folder

- `components.md`: the enforced units and what each publishes.
- `units.md`: classes, modules, functions, interfaces, and data structures, with their kind and ring.
- `dependencies.md`: every source dependency, the forbidden edges, the ports, entry points, and shared data shapes.
- `metrics.md`: stability and abstractness per component.
- `decisions.md`: deferred decisions, accepted trade-offs, intended exceptions, accepted findings.
- `conventions.md`: where a file goes and what it may import; the folder layout the dependency rules assume.

Terms: a *unit* is a class, module, function, interface, or data structure. A *component* is a group of units behind one published interface that tooling enforces. An *edge* from A to B means A's source code names B. *Policy* is business rules; *detail* is databases, frameworks, transports, vendors, UI, and the data shapes they produce. A *ring* is a band of units at one level of distance from inputs and outputs; dependencies point inward.
