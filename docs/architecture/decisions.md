## Cohesion groups

Sets of components expected to change together for one kind of reason. A change whose touched
components all sit in one group is expected; one that spreads across groups is a finding unless
accepted below. A component may belong to more than one group. Proposed by an audit from change
history; confirmed by a person.

| Group | Components | Kind of change it absorbs |
|---|---|---|
| Vertical feature slice | C1 packages/domain, C3 packages/config, C5 packages/ui, C6 packages/infrastructure, the feature component (C7 features/store, C8 features/waitlist, C9 features/accounts or C17 features/assessment-calls), the surfaces that register it (C11 surfaces/public-site, C12 surfaces/client-portal, C13 surfaces/coach-portal), C14 apps/platform/src/server and the migration journal `apps/platform/db` | one user-visible capability delivered end to end, the repository's ticket-cutting unit. A slice usually but not always touches the composition root and the journal, so a member's absence does not on its own make a change uncontained. Confirmed by the owner |
| Waiting-list mode | C1 packages/domain, C3 packages/config, C6 packages/infrastructure, C8 features/waitlist, C14 apps/platform/src/server, C15 app root, C17 features/assessment-calls, `apps/platform/db` | how waiting-list mode is stored, read and switched: the `WAITLIST_MODE` flag's domain reader, its Postgres repository, the waitlist and booking-window consumers, the container that hands one reader to all of them, and the migration that seeds it. The spread across C1, C3, C8, C14 and C15 is owner-accepted; C6 and C17 are added from the code, unconfirmed |
| Coach scheduling | C1 packages/domain, C6 packages/infrastructure, C17 features/assessment-calls, `apps/platform/db` | the coach's own time and room: slot policy, reservation and overlap rules, the coach's window and meeting room, their tables and constraints. Proposed from change history, unconfirmed |
| Adapter-facing contracts | C6 packages/infrastructure, C7 features/store, C8 features/waitlist, C17 features/assessment-calls, C14 apps/platform/src/server | a change to the email, bot-detection or management-auth contract, which lands on the C6 contract and adapter and on every feature that sends or verifies through it at once. Proposed from change history, unconfirmed |
| Design system | C5 packages/ui and its consumers C7 features/store, C8 features/waitlist, C9 features/accounts, C11 surfaces/public-site, C12 surfaces/client-portal, C13 surfaces/coach-portal, C15 app root, C17 features/assessment-calls | a token, primitive or shared look (focus, disabled state, corner, typography) changed once in C5 and taken up by every consumer. Proposed from change history, unconfirmed |
| Coach portal | C1 packages/domain, C5 packages/ui, C13 surfaces/coach-portal, C17 features/assessment-calls | a coach-facing block: a listing use case and its port method in C1, a portal primitive in C5, the coach UI half of the feature, and the dashboard page or navigation in C13. Owner-accepted as a vertical slice |

## Open questions

Written by an audit, which rewrites this section in full; review modes never append here.

- Should `./primitives` split further, given it publishes twelve components across nineteen symbols?
- Should the closed/unavailable/open copy branch move from the three waitlist views (`hero.tsx`, `footer-cta.tsx`, `pricing.tsx`) onto `WaitlistPresentation` if a fourth mode or a fourth consumer arrives?
- Should a feature's Turnstile action constant live in its own `contracts/` rather than in C6 `bot-detection/bot-detection-contract.ts`? C6 names three actions (`WAITLIST_TURNSTILE_ACTION`, `STORE_ACQUISITION_TURNSTILE_ACTION`, `ASSESSMENT_CALL_BOOKING_TURNSTILE_ACTION`), one per protected form, so the adapter package carries a list that grows with the features rather than with the provider. The counter-argument is that the action string is part of the Turnstile submission contract, which is C6's to own. If it moves, it moves as one mechanical follow-up across all three features.
