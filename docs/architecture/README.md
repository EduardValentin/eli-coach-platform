## Shape

The business rules live in `packages/domain` (C1), published as nine subpaths with no root barrel: one folder per entity (`account`, `acquisition`, `cart`, `download-grant`, `email-address`, `feature-flag`, `product`, `waitlist`) plus the interface-only `shared`. Rules are methods on entity classes and `<Verb><Noun>UseCase` classes sequence them. `Waitlist` is the configured waiting-list aggregate: cap and active offer form the aggregate configuration shared by availability and registration workflows. `GetWaitlistUseCase` reads the existing `FeatureFlagReader` on every execution and assembles the plain `WaitlistSnapshot` from the resolved flag, the entity's offer and its computed availability; `JoinWaitlistUseCase` also reads cap and offer directly. The offer object is readonly but its nested representation is not deeply immutable; this R17 cost is explicitly accepted until offer mutation or a second offer model is required. `WAITLIST_MODE=true` enables the waitlist, false or absent disables it, and a read failure is logged through the `Logger` port and safe-enables with unavailable availability. The resulting `waitlist → feature-flag` slice edge enters the sibling index, stays within the use-case ring, and does not close a cycle. The package still declares no dependencies and its tsconfig sets `"types": []`, so neither an external import nor an ambient Node global reaches policy.

Details plug in through policy-owned ports. Each feature under `apps/platform/src/features/<feature>/` holds its adapters, contracts, request-context key, composition, and browser code. `packages/infrastructure` (C6) owns the Postgres feature-flag adapter and table but no port. The single container composition root now constructs one `PostgresFeatureFlagRepository` and one `GetFeatureFlagsUseCase`, then passes the same reader to the platform feature-flag API and waitlist composition. `platform-composition.server.ts` no longer constructs persistence. Routes and loaders still read feature slices from request context; the platform API and public shell each execute the shared stateless reader per request, with no result cache or production write path.

Boundaries remain enforced by dependency-cruiser, package exports and dependency declarations, `knip.json`, package packlists, and the domain-layout check. Their dependency-rule configuration did not change: 35 forbidden dependency rules remain, `domain-slices` forces the new sibling edge through `feature-flag/index.ts`, and `no-circular` rejects a slice cycle. The gates still run through typecheck, build, Vitest, CI, and the Docker builder. The platform package's `files` allowlist emits only `build`; the config, content, domain, infrastructure, and UI package packlists retain their production source and artifacts while excluding colocated test/spec files. The Docker builder asserts that the deployed artifact contains `build/server/index.js`, contains neither top-level `e2e` nor `src`, contains no recursive test/spec file under `node_modules/@eli-coach-platform`, and omits the dev-only test-support package. Environment, Docker, CI, integration, and Lighthouse wiring no longer carry `WAITLIST_MODE`; migration 0018 seeds the persisted flag true instead. E2E setup and teardown change it through a test-only, parameterized Postgres adapter guarded from production imports.

## Reading this folder

- `components.md`: the enforced units and what each publishes.
- `units.md`: classes, modules, functions, interfaces, and data structures, with their kind and ring.
- `dependencies.md`: every source dependency, the forbidden edges, the ports, entry points, and shared data shapes.
- `metrics.md`: stability and abstractness per component; volatility counts the 84 commits in `148d594f..e8690f45`, with the 16 of the domain-model restructure and the seven of the persisted waitlist-mode change (`79fa1e95..f0eb1bf4`) shown separately.
- `decisions.md`: deferred decisions, accepted trade-offs, intended exceptions, accepted findings.
- `conventions.md`: where a file goes and what it may import; the folder layout the dependency rules assume.

Terms: a *unit* is a class, module, function, interface, or data structure. A *component* is a group of units behind one published interface that tooling enforces. An *edge* from A to B means A's source code names B. *Policy* is business rules; *detail* is databases, frameworks, transports, vendors, UI, and the data shapes they produce. A *ring* is a band of units at one level of distance from inputs and outputs; dependencies point inward.
